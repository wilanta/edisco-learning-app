## 1. Free Generation Quota

- Every `User` starts with `freeGenerationsLeft = 3`, set when `onboardingCompletedAt` is populated (not at registration time), so the quota only "activates" once the user has actually completed the onboarding flow.
- **Every generate trigger** (whether from the "New" menu for a new topic, or the "Generate Next" button at the end of a Track) reduces `freeGenerationsLeft` by 1, **regardless of whether the result is a brand-new LLM-generated lesson or a reused one** (explicit decision from Wil).
- The quota decrement happens **after the generate job succeeds** (status `DONE`), not when the request comes in — so if the job fails (`FAILED`, e.g. an LLM error), the user doesn't lose quota. This is important for fairness and must be implemented as a **transaction**: updating `Lesson`/`UserLesson` + decrementing `freeGenerationsLeft` in a single DB transaction.
- When `freeGenerationsLeft = 0`:
  - The "Generate Next" button and the "New" menu form remain visible but disabled, with a clear message that the free quota is exhausted.
  - **No** automatic reset mechanism in the MVP (per `prd.md` §6 — explicitly no monetization/reset).

## 2. Lesson Reuse & Caching (Semantic Similarity)

### 2.1 Decision Flow

```
1. User requests a generation with input: topic (free text) + category (from selection/interests)
2. System generates an embedding from a representation of the topic (e.g. combination of topic + category + level/pace)
3. Vector similarity search on the Lesson table:
   WHERE category = requested_category
   AND isExpiredForReuse = false
   ORDER BY embedding <-> query_embedding   (cosine/L2 distance, pgvector)
   LIMIT 5
4. Take the top-1 candidate. If distance <= SIMILARITY_THRESHOLD:
     -> REUSE: create a new UserLesson referencing that Lesson (wasReused = true)
   Else:
     -> GENERATE NEW: call the LLM, create a new Lesson, store the embedding, expiresAt = now() + 3 months
5. Decrement the user's freeGenerationsLeft by 1 (see §1)
```

### 2.2 Similarity Threshold

> ⚠️ **The exact number can't be finalized without real experimentation** — the cosine similarity threshold for "similar enough" depends heavily on the chosen embedding model and the real-world distribution of user topics. **Implementation recommendation:** start with a fairly strict threshold (e.g. only reuse when similarity is very high, >0.92 on a 0–1 cosine similarity scale) to keep the risk of "user gets a lesson that doesn't quite match the requested topic" low early on, then tune based on real data (log every reuse-vs-generate-new decision along with its similarity score, for periodic manual analysis).
- Don't hardcode the threshold in multiple places — store it as a config/env variable that's easy to tune without redeploying code.

### 2.3 Why Still Consume Quota on Reuse?

Per Wil's decision: from the user's perspective, they still "receive 1 new lesson to study" — it's irrelevant to them whether it was generated by the LLM in real time or pulled from cache. The quota measures **how many lessons the user receives**, not how many LLM API calls occurred. This also simplifies the UX messaging (no need to explain the reuse concept to the user, per `prd.md` §6).

### 2.4 Expiry (3 Months)

- `expiresAt = createdAt + 3 months`, set when a Lesson is first created.
- A scheduled job (cron, runs daily) updates `isExpiredForReuse = true` for all Lessons where `expiresAt < now()`.
- **Expired ≠ deleted.** A Lesson already owned by a user (via `UserLesson`) remains accessible forever on the "Lesson" page, regardless of its expiry status. Expiry **only** affects whether the lesson is a candidate in the vector search step (§2.1 step 3).
- **Business rationale:** older content (3+ months) risks being outdated (especially for tech/coding topics that change quickly), so it's not ideal to keep reusing it for new users — but users who already learned from it shouldn't lose access.

## 3. Content Templates per Category

Each category has a "bank of part types" the AI can choose from when generating (the AI picks a combination of 5 parts from the list below, based on what fits the topic — **varied within a single lesson**, per the assumption in `prd.md` §5).

| Category | Relevant Part Types |
|---|---|
| **Programming/Tech** | `CODE_PREDICT` (predict code output), `FILL_IN_BLANK` (complete a line of code), `MULTIPLE_CHOICE` (concepts), `SHORT_ANSWER` (briefly explain a concept), `MATCHING` (term ↔ definition) |
| **Language** | `TRANSLATE` (translate a sentence), `FILL_IN_BLANK` (complete a sentence), `MULTIPLE_CHOICE` (choose the correct meaning/grammar), `MATCHING` (vocabulary ↔ meaning) |
| **Math** | `SHORT_ANSWER` (step-by-step numeric answer), `MULTIPLE_CHOICE` (pick the correct result/step), `TRUE_FALSE` (validate a mathematical statement) |
| **Science** | `MULTIPLE_CHOICE`, `TRUE_FALSE`, `SHORT_ANSWER`, `MATCHING` (term ↔ definition) |
| **Engineering** | Combination of Math + Science + `SHORT_ANSWER` for practical cases |
| **General (fallback)** | `MULTIPLE_CHOICE`, `TRUE_FALSE`, `SHORT_ANSWER` — the most generic template, used for topics outside the 5 categories above |

> ⚠️ **Needs clarification from Wil:** Is the AI **free to choose** any combination of part types per lesson (e.g. could be 3x MC + 1x fill-in-blank + 1x matching), or does it need a **fixed order/ratio** (e.g. always start with MC, end with short-answer)? Assumption used: **AI freely chooses** the combination most relevant to the lesson's sub-topic, as long as the total stays at 5 parts. Tracked in `open-questions.md`.

### 3.1 Personalization Based on Pace

- `pace = CASUAL` → part complexity/length is tuned lighter (shorter questions, simpler explanations).
- `pace = REGULAR` → default/baseline.
- `pace = INTENSIVE` → parts can be slightly more challenging/dense (e.g. more sub-questions within a part, or a higher concept difficulty level).
- Pace **does not change the number of parts** (stays at 5) — only content depth/complexity, so the data structure stays consistent and the UI doesn't need to handle a variable part count.

## 4. XP & Gamification (Initial Recommended Numbers)

> This is a starting point, not final numbers — easy to tune via config, should not be hardcoded in multiple places.

| Action | XP |
|---|---|
| Completing 1 Part (correct answer) | 10 XP |
| Completing 1 Part (wrong answer, but proceeds after retry) | 5 XP |
| Completing an entire Lesson (5/5 parts) | +20 XP bonus |
| Active daily streak (per day, cumulative) | +5 XP bonus/day |

**Streak calculation:**
- `lastActivityDate` is updated every time the user completes at least 1 Part.
- If `today - lastActivityDate == 1 day` → `currentStreak += 1`.
- If `today - lastActivityDate > 1 day` → `currentStreak` resets to 1 (not 0, since the user was active today).
- If `today - lastActivityDate == 0` (already active today) → no streak change (prevents double-counting).
- `longestStreak` is updated whenever `currentStreak > longestStreak`.

## 5. Weekly League (MVP — Global Leaderboard)

- `WeeklyLeagueEntry.xpThisWeek` accumulates every time a user earns XP (see §4), with `weekStartDate` = the Monday of the current week (use a consistent timezone; recommendation: pick whichever timezone matches your primary user base).
- At the start of every new week (cron job, Monday 00:00 in the chosen timezone), the system:
  1. Finalizes last week's ranking (for history/badge purposes, optional in MVP).
  2. Creates a new `WeeklyLeagueEntry` row for the current week (xpThisWeek = 0) — or creates it on-demand the first time a user earns XP that week (lazy creation, more efficient than bulk-creating rows for all users every week).
- Ranking is computed **on-read** (query `ORDER BY xpThisWeek DESC` when the League page is opened) for the MVP — no need to precompute `rank` in the DB unless traffic is high (a v2 optimization if needed).

## 6. Cost Strategy Summary

1. **Reuse mechanism** (§2) is the main cost reducer — each reuse = 0 LLM calls for content generation (only 1 embedding call for the similarity query).
2. **Cheap models for general categories**, more precise models (where needed) only for categories sensitive to answer correctness (Math, Programming) — see `architecture.md` §3.
3. **Structured output/JSON mode** reduces the need for retries due to parsing failures (retries = doubled cost).
4. The embedding model is chosen to be cheap because it's called on **every** generate request, even when the result is a reuse — this is a fixed cost per generation that must be kept as low as possible.
