# PRD — Edisco

> Edisco is an AI-powered, Duolingo-style learning app for any topic. This document is the product source of truth. Derived documents: `srs.md`, `architecture.md`, `data-model.md`, `business-logic.md`, `api-spec.md`.

---

## 1. Product Summary

A learning app with Duolingo-style gamification, but **the content is not a fixed curriculum** — it is generated by AI based on whatever topic the user requests (tech, coding, languages, engineering, math, science, or other general topics).

**Value proposition:** "Learn anything, the way Duolingo teaches languages."

**Platform:** Responsive web app — must work well on mobile, tablet, and desktop (not a native app, but mobile-first responsive web, PWA-ready).

---

## 2. Target User & Problem Solved

- Users who want to learn a niche/specific topic not available on structured course platforms (Duolingo is language-only, Coursera is too heavy/formal).
- Users who enjoy gamification (streaks, XP, leaderboards) as learning motivation, but want topic flexibility.
- Casual learners who want to "try learning first" before committing to a full course.

---

## 3. Onboarding Flow

**Mandatory** sequence, must not be reordered:

1. **Welcome screen** — brief product introduction, illustration/animation, "Get Started" CTA.
2. **Ask Interests** — multiple selection (not single choice). Options are broad categories (e.g. Programming, Foreign Language, Math, Science, Engineering, Career/Soft Skills, Other — with free text if "Other" is selected). At least 1 must be selected.
3. **Ask Pace** — single choice. Example options: *Casual (5–10 min/day)*, *Regular (15–20 min/day)*, *Intensive (30+ min/day)*. Pace is **stored as a preference**, used to personalize the amount/depth of generated Parts (see `business-logic.md`), not just cosmetic.
4. **Register/Login** — placed last, after the user has already "invested" time answering the two previous questions (commitment psychology). Interest + pace data is stored temporarily (local state/sessionStorage) before the account is created, then attached to the account once registration completes.

> ⚠️ **Open question for Wil:** Can onboarding be skipped (e.g. a "Skip" button on the interest/pace steps)? Assumption used: **cannot be skipped**, because this data personalizes the first generation. Please confirm — tracked in `open-questions.md`.

## 4. Menu Structure (Main Navigation)

Bottom nav (mobile) / sidebar (desktop) with 5 items:

| Menu | Function |
|---|---|
| **Track** | Home page (equivalent to Duolingo's home) — shows the visual path of generated lessons for the currently active topic, one node per lesson, with progress. |
| **Lesson** | List of all lessons the user has generated, grouped by topic/track, repeatable. |
| **New** | Entry point to generate a new lesson/track — topic form + options, consumes free quota. |
| **League** | Weekly XP-based leaderboard, league/group system (see `business-logic.md`). |
| **Profile** | User data, learning stats, settings, remaining generate quota, streak. |

> ⚠️ **Needs clarification:** Can a user have **more than one active track/topic at once** (e.g. learning Python and Spanish simultaneously, each with its own Track), or only one active track at a time that must be switched? This significantly impacts the Track and Lesson page design. Assumption used: **users can have multiple tracks**, and the Track page has a selector/tab to switch between tracks. Tracked in `open-questions.md`.

## 5. Content Model: Lesson & Part

- 1 **generate** action = 1 new **Lesson**.
- 1 Lesson consists of **5 Parts**.
- Each Part's format **adapts to the topic category**:
  - **Categories with dedicated templates:** Tech/Coding, Language, Engineering, Math, Science. Each category has a different *part-type template* (details in `business-logic.md` §Content Templates) — e.g. coding can be "predict the output" or "complete the code," language can be "translate," math can be "step-by-step calculation."
  - **General/other categories:** use a *general template* (e.g. concept-understanding MC, true/false, short answer) — a fallback that isn't topic-specific.
- To continue a track (adding a new lesson to the same track), the user clicks the **"Generate Next"** button at the bottom of the track. This action **consumes free quota**, the same as the first generation.

> ⚠️ **Needs clarification:** Does each Part within 1 Lesson have a **uniform question type** (e.g. all 5 parts are multiple choice) or can it **vary** within a lesson (part 1 MC, part 2 fill-in-blank, etc.)? Assumption used: **varied**, since it's closer to Duolingo and more engaging. Tracked in `open-questions.md`.

## 6. Business Model (MVP — No Monetization)

- Every new user gets **3 free generate quota** after completing onboarding.
- **No paywall.** Once the quota runs out, the user is clearly informed the quota is exhausted (no daily/weekly reset mechanism in the MVP, no payment).
- Quota is **lifetime per account** (not per track), counted across all generate activity (both initial generation and "Generate Next").
- **Lesson reuse/caching** (full detail in `business-logic.md`):
  - When a user requests a generation, the system first checks whether a **semantically similar** lesson (via embedding similarity) already exists — generated previously by another user or the same user.
  - If a similar, **non-expired** lesson is found (< 3 months since generation), the existing lesson is **copied/assigned** to the user without calling the LLM again (cost savings).
  - This reuse **still consumes the user's free quota** (counted as 1 generation), since from the user's perspective they still receive 1 new lesson.
  - Expired lessons are **not deleted** from the database — they are simply no longer reuse candidates for new generations. They remain accessible to users who already own them on the Lesson page.

> ⚠️ **Needs clarification:** Should users be told/made aware that a lesson they received is a reuse result (not generated "specifically" for them), or should this be hidden (from the user's view, everything feels like a new generation)? Assumption used: **hidden** — the user doesn't need to know this detail, they just see a new lesson appear. Tracked in `open-questions.md`.

## 7. Gamification

### 7.1 XP & Progress
- XP is earned from completing a **Part** (not only a full Lesson), so progress feels granular and rewards come quickly.
- Recommended scheme (adjustable, see `business-logic.md` for exact numbers):
  - XP per completed Part (consistent base XP).
  - Bonus XP for completing an entire Lesson (5/5 parts) at once.
  - Daily streak bonus XP (encourages daily retention, consistent with the original Duolingo mechanic).

### 7.2 Streak
- Calculated based on days the user completes at least 1 Part.
- Freeze/streak-saver details **not yet specified** — recommended as a v2 feature; MVP only needs a simple streak counter.

### 7.3 League (Weekly Leaderboard)
- Weekly reset, ranked by total XP earned during the current week.
- MVP recommendation: **one simple global league** (all users on a single leaderboard) first; Duolingo-style promotion/demotion (Bronze/Silver/Gold League with small groups) is **v2**, since it needs sufficient user volume for meaningful grouping.

> ⚠️ **Needs clarification:** Is league grouping (e.g. per 30 users) required for the MVP, or is a global leaderboard sufficient? This determines backend complexity (weekly grouping job). Assumption used: **global leaderboard first**, grouping follows in v2. Tracked in `open-questions.md`.

## 8. Non-Functional Requirements

- **Fully responsive:** mobile / tablet / desktop breakpoints; UI components (especially the visual "track path") must remain comfortable to use on small screens.
- **Generation performance:** the generate process (LLM call + embedding check) is estimated at 10–30 seconds → **must not block the UI**, must have a clear loading state / async job (details in `architecture.md`).
- **Low operational cost:** LLM selection & caching strategy are explicitly designed to minimize cost (see `business-logic.md` §Cost Strategy).
- **Not overengineered:** even though FE/BE are separated, avoid granular microservices without strong justification at the MVP stage — just **2 services** (FE, BE) + a separate job worker for async generation (rationale in `architecture.md`).

---

## 9. Explicitly Out of Scope for MVP

- Payment/subscription system.
- Audio/listening exercises (requires a separate TTS pipeline).
- Complex league grouping/promotion-demotion.
- Streak freeze / streak repair.
- Native mobile app (iOS/Android) — responsive web/PWA only.
- Multi-language UI (assumes a single UI language for now; copy can be localized as needed).
